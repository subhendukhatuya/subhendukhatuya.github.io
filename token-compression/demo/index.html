Predict, Allocate, Guide

We give a batch of questions one shared token budget and decide, question by question, how much of it each one gets. This page walks through the idea on a small made-up batch of eight questions. The slider sets the total budget, and everything below is recomputed from it.

Estimating how much each question needs

Before the model writes anything, we run one forward pass over the question. That pass gives two kinds of signal at almost no cost: simple features of the text, and the model's hidden state at a middle layer. A small predictor turns them into an estimated need with an uncertainty range, and into a probability that the question can't be solved at all.

What the choice of features does to this batch

Same total budget, same allocation and guidance; only the predictor's input changes. The last row uses the true needs, which no real system has.

Why both kinds of features: text features are cheap and the same for every model, but they judge a question by its surface. Q3 looks hard because it is long and full of numbers; Q4 looks easy because it is short. The hidden state reflects how the model itself represents the problem and gets those two right, but it is less sure about Q2 and Q5 and only weakly flags Q8. Together they give the same allocation as the true needs in this example.

2

Splitting the budget

All three spend the same total. The uniform split gives every question an eighth. Predictive Scheduling funds the questions it expects to be cheapest first and stops the model at the limit. We size each budget for guided decoding, which needs less than the full natural length, add a margin where the estimate is uncertain, and give a question that looks unsolvable only a small cap.

Keeping the model inside its budget

A budget is only useful if the model can keep it. Budget forcing stops generation when the budget is hit, often mid-derivation. Budget Guidance steers decoding as the budget runs out, so the model skips optional re-checking and writes its conclusion. Pick a question and a budget, then play both side by side.

Re-planning halfway through

At a checkpoint (600 tokens here), easy questions are already done and Q8 has hit its cap. The unspent budget goes back to a shared pool. The remaining-length estimate from guidance is now sharper than the prefill prediction, so the allocator re-plans the open questions: over-padded ones give tokens back, under-funded ones receive them. In the first plan Q2 (underestimated) and Q7 (left short) would fail; after re-planning both are correct.

Novel contributions

  1. Need estimation from text features and hidden states together. One forward pass over the question gives both. The predictor outputs an estimated need with an uncertainty range and a probability that the question can't be solved, instead of a single number from one source.
  2. Predictors judged by the allocation they produce. We score a predictor by how many answers the batch loses when its estimates are used in place of the true needs, not by its average length error.
  3. Allocation that plans for uncertainty and for failure. Budgets are sized for guided decoding, padded where the estimate is unsure, and a question that looks unsolvable gets only a small cap, so it can't absorb the budget others need.
  4. A different budget for every question, kept without cutting the model off. Budget Guidance has so far been used with one budget for all questions. We apply it per question, with targets that differ by two orders of magnitude within one batch.
  5. Re-planning while the batch runs. At checkpoints, tokens left over by finished or capped questions are handed to questions that are running short, using the sharper remaining-length estimate available during generation.
  6. Energy per correct answer as the headline measure. Beyond tokens, we measure GPU energy in a serving engine, where a few very long requests can cost more than their token count suggests.
